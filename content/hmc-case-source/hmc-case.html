01 / A VERY PERSONAL PROBLEM

起点其实很简单。
我不想再同步一遍了。

“我懒得在切换 Agent 时
反复手动同步上下文。”

Hermes、Codex、网页端 Agent，我都在用。切换的时候，我想带过去的不是整段聊天记录，而是：现在做到哪，什么仍然有效，下一步是什么。

于是我做了 HMC。Agent 可以留下结构化更新，系统把它们整理成一份能继续工作的现状。想查某个判断从哪里来，再回到历史里看。

不是让它什么都记住。先把“现在”说清楚，就已经很有用了。

不是这次的重点

可能和这件事有关？

明确的当前事项、活跃点子和摘要

02 / HISTORY IS NOT THE PRESENT

发生过的事，
和现在要做的事，分开放。

Records 留下完整历史，
Current Context 给出工作起点。
它们不是两份随意改写的摘要。

01 / ARCHIVE≡

Records

更新来自谁、发生在什么时候、原始内容是什么，都留下来。

03 / HUMAN VIEW

人不需要埋进原始记录里。

界面把当前状态、时间线和待确认候选分开。
既能检查来源，也保留最后确认权。

看现状 · 查来源 · 确认候选

03 / ONE RECORD, END TO END

“先记着”，
不等于“现在就做”。

自动记录器可以提议，
但不能替我决定什么已经算数。
让一条候选走一遍，就能看见这道边界。

✳ 自动记录器可以提出候选；Agent 也可以主动同步。示例为脱敏数据，不代表真实个人状态。

05 / WHEN THINGS ARRIVE WRONG

同步不能
“差不多对”。

重复、迟到、坏文件，都要有明确结果。
下面三组是规则示意，
不会连接真实 HMC，也不会写入个人数据。

IDEMPOTENCY / 幂等

送了两次，
也只能算一次。

同来源、同记录编号、同内容，返回 duplicate；编号相同却换了内容，就报冲突，不能顺手覆盖。

演示编号、时刻与条目只用于解释规则。

还有一道边界

同名，也不一定是同一个对象。

对象内部按 分组 + 来源 + external_id 区分。不同 Agent 的同名对象不会被误并成一条；共享读取视图，不等于抹掉来源。

06 / WHAT EXISTS, WHAT DOESN’T

能继续工作的现状，
也包括清楚的边界。

它牺牲了一部分全自动的便利，
换来有来源、能检查、能明确修正的状态。
不是要把所有记忆问题一次解决。

02

先服务一个人，先在本地跑。

当前是单用户、本地优先。公开部署前，仍需要 TLS、完整的用户边界和更可靠的共享限流。

03

还在收敛，不急着继续加功能。

早期模型仍留下兼容层。接下来要继续收敛数据语义，而不是让功能无限生长。
